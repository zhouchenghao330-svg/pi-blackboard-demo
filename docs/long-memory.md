# 长期记忆：人物、时间、地点、主题

## 问题与范围

Pi 会保存单个会话的对话历史，但新会话不会自动获得此前人物、事件、地点和主题的当前状态。现有 `search_memory` 可以回查旧记录，不能代替一份持续维护、可纠错的短记忆。本模块只维护这四类信息，不复制会议全文或 PDF Blackboard。

## 存储

- `data/memory/history.jsonl` 是追加的操作日志，记录版本、操作、修改前后、操作者和来源。服务启动时从日志重建当前状态。
- `data/memory/memory.md` 是当前有效条目的可读视图，按人物、时间与事件、地点、主题分组。标题和条目合计最多 2000 个 Unicode 字符。每条有短 ID，便于精确修改。
- 单条事实必须可回溯到用户发言或会议分析的原文行号。模型自己的回答、PDF、网页和 Blackboard 不能单独成为“用户长期记忆”的事实来源。会议中的相对日期不按上传日期擅自换算。
- 删除和合并只改变当前视图；旧版本保留在日志中。当前状态与完整历史分离。
- 用户明确要求长期保留的条目由主 Agent 标记 `pinned`，快照以 `!` 标识；后台不能修改、合并或删除它。

## 主 Agent

- 系统提示词明确：主 Agent 有义务主动维护记忆。用户明确要求记住、更正、忘记，或对话中出现有持续价值的人物、时间事件、地点、主题时，主动调用工具；不靠关键词表触发。后台维护器只负责补漏、去重和压缩，不能作为主 Agent 不维护的理由。
- 写入只暴露一个 `memory` 工具。每次调用只操作一条：`add / update / delete / merge`。接受后台候选时传入 `proposal_id`，程序使用候选保留的原始来源并校验操作类型；工具返回结果与剩余容量。另有 `search_memory` 用于检索原始对话和会议，不承担短记忆写入。无 `get_long_memory` 工具。
- 主 Agent 在新会话第一次真正调用模型时读取一次 `memory.md`。同一会话的普通轮次不重载；Pi 成功压缩后，在下一次调用模型前重读。服务重启恢复会话时也重读。主动调用 `memory` 后，工具结果已告诉它自己的改动。后台不会直接修改记忆，而是通过隐藏通知给它候选操作；同一会话的普通轮次不重载快照。
- 修改目标若已被其他会话更新，工具先返回冲突和当前条目，不静默覆盖。容量超限时拒绝写入并告知字数；主 Agent 应合并或缩短重复条目。快满时也检查可能过时的内容；若缺少明确失效依据，先问用户再删除。不能仅因条目久远或容量紧张删除，也不能为了腾空间删掉用户明确要求保留的重要事实。

## 后台维护

- 每个完整用户轮次后，持久化待处理的用户输入和最终回答。累计 5 轮时异步扫描；会议分析成功完成时，直接异步扫描会议结构化事实。空结果允许，后台任务不阻塞主回复。
- 后台扫描器读取当前记忆、字数预算及未处理片段，只生成逐条候选操作。聊天里的助手回答仅供理解上下文，不能独立作为事实依据。会议只使用带行号的结构化事实；失败的会议分析不产生候选。
- 候选持久化在 `data/memory/proposals.json`。投递给主 Agent 的隐藏 follow-up 仅包含候选 ID、操作与内容，不重复传送会话片段；原始来源保存在后台，接受时由 `memory` 工具引用。主 Agent 根据当前会话历史决定是否执行。用户消息仍按 Pi 的 steer 优先于后台 follow-up。候选不会自动改写记忆，普通聊天无需为此显示额外回复。
- 接近容量上限时，扫描器可以提出缩写或合并；只有资料明确证明失效才提出删除候选。扫描失败的批次保留待处理状态。候选生成时若记忆版本发生变化会重试；最终写入由 `memory` 工具进行容量、来源和版本校验。

## 前端与验收

- 对话流插入简短的“记忆已更新”记录，展示新增、修改、删除、合并和来源；可展开看前后内容。后台候选在主 Agent 接受并真正写入后才显示为改动。界面轮询持久化日志，不把 UI 浏览动作注入 Agent 上下文，也不单开右侧面板。
- 会话 A 讨论会议中的人、日期、地点、主题；新建会话 B 可直接利用短记忆回答，并能用 `search_memory` 回查细节。用户纠正后出现一次 `update` 历史；新会话 C 读取更正版本。接近 2000 字时通过合并/压缩保持可写，超限操作不得损坏旧状态。
