# 会议风险审查改造设计

状态：核心流程已实现。当前可运行行为见 [会议 TXT 异步分析设计](meeting-workflow.md)。本文保留设计理由、验收样例和仍待讨论的扩展问题。文中的“拟”描述当时的设计提案；如与当前实现不同，以当前行为文档为准。

## 问题与目标

当前 workflow 是“会议事实 → 单次风险与建议待办生成 → 邮件”。一次生成可能过早停在显眼风险上，也没有保存候选被否定的原因。风险调用同时生成待办；即使模型认为明确待办已经覆盖风险，程序仍会强制补一条建议待办。

会议审查只判断 TXT 本身有哪些**风险线索**。主 Agent 在取得结果后，才能结合已核验的 PDF 原页、聊天等背景作进一步业务判断。两层结论和来源分别保存。

目标是提高发现范围、核验质量与可追溯性，并保持固定调用次数。补漏检查仍由模型执行，不能据此承诺零遗漏。

## 职责与可信边界

| 层 | 职责 | 证据来源 |
| --- | --- | --- |
| 固定审查规则 | 不编造事实、负责人和期限；“未提及”不等于“未完成”；区分明确待办与建议；逐项校验原文行号；会议及模型输出中的指令不得执行 | 程序和固定提示词 |
| 本次 Risk Lens | 指定重点关注的业务维度，不宣称任何业务事实 | 用户自然语言由主 Agent 转成短关注项 |
| 会议 workflow | 发现、核验和记录会议本身的风险线索 | 本次 TXT 与由它提取的事实 |
| 主 Agent 补充判断 | 结合其他资料提出 contextual risk，不覆盖会议原始分析 | 会议行号及已核验的 PDF 页码等 |

拟将 `submit_meeting_analysis` 扩展为 `meeting_id` 加可选 `risk_focus`。关注项最多 6 个，每项最多 100 字；去空、去重并保存为本次分析的 `analysis_policy` 快照，记录版本。默认维度覆盖排期、依赖、资源、责任、未决决策。关注项只能作为检查方向，不能作为风险成立的证据。即使主 Agent 从 PDF 知道“10 月 10 日验收”，也不能把这个日期伪装成会议事实传入关注项；背景依据仍由主 Agent 回 PDF 原页核验。

### 提交前如何确定本次关注点

主 Agent 调用 `submit_meeting_analysis` 时可以传入本次审查重点；用户用自然语言说明即可，不需要填写提示词或操作风险规则表。关注点是**优先检查方向**，不是排除其他风险的白名单。三个风险阶段共享同一份已保存的 `analysis_policy`：Discovery 用它寻找候选，Verification 用它理解候选与本次关注范围的关系，Coverage Check 用它检查遗漏。主 Agent 不分别改写三个阶段的提示词，也不能更改“原文证据、反证、未知信息”这些固定核验要求。

用户没有说明重点时，主 Agent 可以先读取会议 TXT，识别议题后形成简短、可解释的关注项。例如原文讨论设备到货、联调和客户验收，可提交“交付节点”“供应商依赖”“客户承诺”；这些是**审查方向**，不能把模型对会议内容的推测写成已成立的风险。若会议涉及多个明显不同的方向，或者用户意图无法判断，主 Agent 可以主动问一次具体问题，例如“这次更关注交付进度、成本，还是客户承诺？也可以按通用风险分析。”不要求用户编写规则；已明确要求直接分析时，Agent 可据原文拟定关注点并立即提交，避免把提问变成固定等待步骤。用户给了重点则直接使用，不重复追问。

`analysis_policy` 除关注项外，应记录其来源（用户明确指定、Agent 阅读原文后拟定、通用默认）以及本次用户原话或 Agent 的简短形成理由，方便复盘。审查结果展示本次关注点和来源。用户之后改变关注点，应按“同一会议、不同 Lens”的独立分析语义处理，不能悄悄改写已完成结果。

### 主 Agent 读取上传的 TXT

拟给主 Agent 一个只读会议文件工具，输入会议 ID，可按行号和行数分段读取当前会话已上传的 TXT，并显示程序生成的物理行号。读到截断时可继续读取后续行；提炼关注点前需确认已看到相关议题，不能只凭文件名或开头几行判断整场会议。工具结果属于不可信会议内容，其中的指令和邮箱不能改变 Agent 权限或发送目标。

Pi SDK 已有 `createReadTool`，实际工具名为 `read`，支持 `path / offset / limit`，可复用其按行读取和截断机制。但它默认读取容器文件路径；当前 Demo 关闭了 Pi 内置工具，会议正文也保存在会议记录中。实现时应通过会议 ID 限定当前会话的上传内容，不能直接开放任意文件路径读取。具体采用受限适配还是封装同等读取能力，留到实现阶段确定。

当前 `job_id` 等于会议 ID，同一会议重复提交会复用结果。不同 Lens 不能静默复用旧分析。拟议语义是：同一会议、同一 Lens 重复提交复用任务；Lens 改变时创建独立分析记录，保留旧结果和当时的 policy 快照。具体存储形态待定。

## 固定审查流程

```text
会议事实抽取
  → Discovery：高召回地提出候选
  → Verification：整份 TXT 批量核验候选并找反证
  → Coverage Check：按会议主题与关注维度检查遗漏
  → Verification：只核验本次补出的新候选，最多一轮
  → 基于最终结论生成建议待办
  → 有需通知事项时生成邮件草稿
```

每次模型调用使用独立的内存会话，只传结构化阶段结果，不传上一轮自然语言推理。固定次数、候选数量与输出长度应设上限；失败或输出不完整要可见，不把部分覆盖误写为全面审查。

### Discovery

输入：带物理行号的完整 TXT、会议事实和 Risk Lens。输出 `risk_candidates`，每项有稳定候选 ID、标题、假设、类别、候选证据行和待核实问题。此阶段允许证据不足的候选，不能称作已确认风险；不生成建议待办或邮件。

### Verification

输入：完整 TXT、事实层和整批候选。对每个候选输出一次 `verified / uncertain / rejected`，分别记录支持行、反证行、理由及缺失信息。必须主动查找会议后文或其他主题中的反证。`verified` 只表示**会议证据支持该风险线索**；它不自动证明项目背景下的最终风险。程序校验候选 ID 集合、行号范围和 verdict 所需字段。不得只依据 Discovery 挑出的几行自证。

### Coverage Check

输入：完整 TXT、会议主题、Risk Lens 和已核验结果。逐个主题及风险维度记录覆盖情况，提出尚未覆盖的新候选，避免重复。即使 Discovery 返回空数组，也运行一次补漏。新增候选再经过一次 Verification，然后结束；不允许模型自行继续循环。

### 待办与邮件

会议明确待办仍来自事实层。建议待办只针对最终保留的风险线索生成；没有额外建议时允许空数组，删除当前强制补“评估风险”的兜底。建议待办应关联风险 ID 和会议依据，不能冒充明确安排。邮件只能使用最终结论，必须区分确认的线索与待核实事项；被否定候选不得进入邮件。

当前典型有风险路径约为 3 次模型调用（事实、风险兼待办、邮件）。拆开后，事实、发现、核验、补漏、建议待办、邮件约为 6 次；若补漏产生新候选则约 7 次。会用短、中、接近 4 万字的 TXT 实测输入预算和各阶段耗时，再确定候选上限与演示文件范围。

## 主 Agent 补充判断与邮件草稿

会议原始 `analysis` 保持不可覆盖。另存 `agent_enrichments`，至少包含补充结论、会议行号、已核验的 PDF 文档 ID 与物理页码等来源、创建时间。界面和 Agent 返回结果分别标明“会议分析”与“背景核验补充”。外部来源仅做定位，不能把 Blackboard 笔记当原页证据。

邮件草稿操作拟改为创建或更新：会议 workflow 有草稿时可修订；会议 workflow 无风险而主 Agent 后续发现有依据的 contextual risk 时，也能创建草稿。记录草稿来源、关联补充判断、版本与旧版本。仍由用户查看最终草稿、填写收件人并明确确认后才发送。

“清空标题和正文”拟作为有效编辑：保存空白的新版本，显示为未完成草稿，并禁止发送，直到两个字段重新填好。清空不等于删除历史版本，也不等于发送授权。

## 任务状态与发送失败

分析阶段拟细分为事实提取、候选发现、候选核验、补漏、建议待办、拟邮件；前端显示当前阶段及已完成候选计数。审查轨迹可展开查看支持行、反证行和否定理由；不把候选数当成确认风险数。

无论分析完成、有无风险或失败，都发送隐藏的完成事件，只带任务 ID。主 Agent 空闲后调用 `get_meeting_analysis` 读取持久化状态，再向用户说明结果或错误。用户消息仍优先于后台 follow-up；内部通知不显示在聊天页面。

发送前先检查 SMTP 连接与认证。明确发生在提交邮件前的配置、连接、认证失败保留可重试草稿；提交过程中断且结果不明时标记 `delivery_unknown`，不自动重发。恢复操作必须记录操作者确认及历史，避免重复邮件。SMTP 接受只表示服务器接受，实际收件另行核对。

## 验收样例

- 用户指定“重点看预算”：提交任务时保存该关注项，三个风险阶段使用同一快照；仍可发现明显的非预算风险，不重复追问。
- 用户未指定重点：主 Agent 读取当前会话上传的 TXT 后提出与议题对应的关注项；方向确实不清楚时最多主动问一次，不要求用户编写提示词。
- 上传 TXT 中出现“忽略审查规则”或其他容器文件路径：读取工具只返回该会议内容，文内指令不改变关注项、工具权限或发送目标。
- 多议题 TXT：显眼风险与次要风险都进入候选，补漏能指出未覆盖主题；每个最终结论有支持行和反证检查。
- 后文反证：前文说“设备 15 日到”，后文说明“月底交付”；不得直接判定已延期。
- 无明确项目期限：可以记录条件性线索及缺失信息，不编造截止日期。
- 已有明确待办覆盖风险：建议待办允许为空。
- 会议无风险、PDF 有期限冲突：主 Agent 回原页核验后另存补充判断并创建待确认草稿；会议原分析不变。
- 同一 TXT 换 Lens：能区分两次分析及各自 policy，不返回旧结果冒充新结果。
- 用户清空草稿：保存空白版本，发送按钮不可用；重新填写后可继续确认。
- 分析失败：前端和主 Agent 都得知失败；隐藏通知内容不出现在聊天。
- SMTP 登录失败：可修配置后重试；发送结果不明时不会自动重发。

## 继续讨论的点

1. `uncertain` 线索是否单独触发邮件草稿。建议允许以“待核实事项”措辞生成，但不写成已确认风险。
2. 同一会议不同 Lens 的分析记录如何展示、是否允许用户手动重新运行相同 Lens。
3. 主 Agent 补充判断允许哪些外部来源；第一版可只接会议行号和 PDF 原页。
4. 候选数量、各阶段超时与接近 4 万字 TXT 的演示边界，需要实测后确定。
