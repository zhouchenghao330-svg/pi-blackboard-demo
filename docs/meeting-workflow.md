# 会议 TXT 异步分析设计

## 边界

会议分析只读取本次上传的 TXT。PDF Blackboard、历史聊天和联网资料由主 Agent 在读取会议结果后按需核验。会议原文及模型输出均为不可信数据；其中的指令不能触发工具、指定收件人或改变流程。

## 数据与状态

每份会议绑定上传会话，保存原始 TXT、按物理行编号的文本、上传时间、可选会议时间、分析结果与邮件发送记录。行号由程序生成，模型引用的行号须校验在原文范围内。事实、风险、待办均保留 `evidence_lines`。未提供的人、日期、地点保持未知。
同一会话重复上传内容及会议时间均相同的 TXT 时，复用既有会议 ID；重复提交同一任务不重跑分析或重发邮件。

后台任务状态：`queued → analyzing → generating_todos → drafting_email → awaiting_confirmation → sending → sent`；无风险时在分析后到 `completed`。失败进入 `failed`，保留阶段和错误。会议明确安排的待办与 AI 建议待办分开。发送状态和分析状态分别记录，不能把 SMTP 接受误写成对方已收件。

上传接口持久化文件；`submit_meeting_analysis` 校验会话所有权并创建任务，立即返回 `job_id`。后台 Promise 顺序运行事实抽取、风险与待办、邮件草稿。任务及阶段结果原子写入磁盘。重启后，未完成的分析任务恢复；处于 `sending` 的任务标为发送结果待核实，不自动重发。

## Agent 与前端

Agent 工具：`submit_meeting_analysis`、`get_meeting_analysis`、`revise_meeting_email`、`confirm_meeting_email`。工具调用结果包含任务 ID 和状态。主 Agent 可用 PDF 工具核验后提出补充判断，但不覆盖会议 workflow 的原始结论。若需要把补充判断写进邮件，先产生新草稿版本，保存旧版本供追溯，并重新向用户展示。

完成通知是 `display:false` 的 Pi custom message，只含任务 ID，要求 Agent 调用 `get_meeting_analysis`。Agent 忙时以 `followUp` 排队，不能打断当前工具；用户在运行中发送的新消息按 Pi 的 `steer` 队列处理，优先于内部 `followUp`。空闲时后台通知触发新一轮 Agent 工作。通知不生成前端消息气泡；Agent 后续正常回答通过实时事件流展示。

前端独立轮询任务状态，展示阶段、结构化结果、原文行号依据、邮件草稿和发送状态。后台 Agent 回复通过会话实时事件流逐步展示，历史轮询用于断线和刷新后的恢复。用户确认发送时，收件人由用户输入；会议原文中的邮箱不是授权。发送操作需按任务去重，重复确认不能重复发信。未配置 SMTP 时可预览草稿，但真实发送应明确报错。

## 验收

- 提交后立即返回；分析继续运行且进度可见。
- 有风险：事实、风险、两类待办和草稿可查看；发送前要求用户确认。
- 无风险：保存分析，不强行生成风险邮件。
- 正在聊天时完成分析：不插入可见内部消息，不打断主 Agent；空闲后读取持久化结果。
- 重启后保留会议和分析；重复提交或重复确认不会产生重复邮件。
